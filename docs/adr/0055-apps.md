# ADR 0055 — Apps: model–update–view, motion on the compositor, and a path to desktop and mobile

- **Status:** **Accepted — Phases 1 and 2 implemented.** The runtime and component library are
  `std/ui.helix`, compiled into `helix` (`import std.ui`); views render and diff in Rust
  (`view_html`, `view_diff`); `examples/apps/` holds a gallery of every component, a regression
  explorer and a stopwatch, driven in Chromium in CI with zero axe-core violations, and every
  app's replay is byte-identical on all three engines. Phases 3–6 are the plan below.
- **Date:** 2026-11-06
- **Deciders:** Areeb + Claude
- **Related:** [ADR 0006](0006-concurrency-and-scale.md) (no `async`, no user threads — this
  keeps both), [ADR 0016](0016-build-and-packaging.md) (`helix build`, the WASM/WASI edge build it
  deferred), [ADR 0021](0021-capability-sandbox.md) (what an app may touch),
  [ADR 0023](0023-hbc-emitter-artifact-format.md) (why HBC, not WebAssembly, is the bytecode).

## Context

The question was whether Helix can build GUI applications — desktop, eventually mobile — with
animation and components that feel first-rate and use the hardware well. Two things made it a
real question rather than a wish:

1. **The language already has the right shape.** Values are immutable; the HTTP server is a pure
   `(request) → response` handler folded over a stream; state is threaded through a
   tail-recursive loop, not mutated. That is exactly the Elm architecture — model, update, view —
   which is the one UI architecture that needs neither mutation nor callbacks nor `async`.
2. **Most of Stage 1's plumbing exists.** `listener.wait(conns, ms)` blocks on the listener, every
   open connection and a timer at once; `conn.sse()`/`send` push without blocking; `to_json` /
   `parse_json`, `html_escape`, the SVG chart helpers and `run` (process authority) are shipped.

### What the foundation lacks today (measured 2026-11-06, `053a77d`)

| Need | State | Evidence |
|---|---|---|
| An event loop that multiplexes clients, a timer and state | **Have** | `examples/api/event_server.helix`; the prototype's `serve` |
| Push to the client | **Have** (SSE) | `conn.sse()` / `send`; ~0.7 ms per event round trip measured |
| WebSocket | Missing — **not needed** for Stage 1 | SSE down + POST up carried every interaction |
| Opening a browser / window | Partial | `run(program, args)` works but is per-OS (`xdg-open` / `open` / `start`) |
| A tree diff in Rust | Missing | the prototype sends whole HTML; the client morphs |
| A binary channel (arrays → typed arrays) | Missing | JSON only; fine for a fit, not for 10⁶ points |
| A native window | Missing | no `wry`/`tao`; Linux would need WebKitGTK, so not the static musl artifact |
| A main thread for the window | **Conflict** | evaluation runs on a spawned big-stack thread (`run_on_big_stack`); macOS needs the window's event loop on the main thread |
| WebAssembly build | **Blocked at dependencies** | `cargo check --target wasm32-wasip1 --no-default-features`: `faer` → `spindle` → `atomic-wait` has no wasm platform. `wasm32-unknown-unknown`: `getrandom` needs its `js` backend. Behind those: `libc` is a hard dependency with 48 Unix-specific sites, and `std::net` is used by `serve.rs` and the PostgreSQL client |

## Decision

### D1 — An app is three values: `init`, `update(model, event) → model`, `view(model) → tree`

```helix
ui.app({
  title: "Regression explorer",
  init: {degree: 3, seed: 7, dark: false},
  update: (m, e) => match e.msg { "degree" => {...m, degree: e.value}, _ => m },
  view: (m) => ui.card("Degree {m.degree}", [ui.slider("degree", 1, 9, m.degree), chart(m)]),
})
```

An event is a record `{msg, value}`. `update` is folded over the event stream exactly as a server
handler is folded over requests: no mutation, no callbacks, no `async`, no new concurrency (ADR
0006 holds). A failing `update` is caught (`try`) and the model is kept — the prototype logs and
carries on, because one bad event must not end an app.

### D2 — A view is data

Elements are records `{tag, props, children}`, built by ordinary functions (`ui.card`,
`ui.slider`, `ui.el`). The tree is rendered by a renderer the program never names. Three things
follow, and they are the reason:

- **It is testable without a browser.** `ui.replay(spec, events)` returns every screen of an event
  log. The explorer's four-event session renders byte-identically on the JIT, the VM and the
  tree-walker — the correctness model ([AGENTS.md](../../AGENTS.md)) now covers user interfaces.
- **It can be diffed** — first on the client (the prototype), then in Rust (Phase 1).
- **The renderer can change** without touching an app: HTML in a web view now, a native GPU
  renderer later if it ever earns its cost (see "Rejected").

### D3 — Helix decides what the screen IS; the compositor decides how to get there

At 120 Hz a frame is 8.3 ms. An interpreter round trip per frame would stutter the moment the
model does real work, so **no Helix code runs per frame, ever.** Motion is declared:

```helix
ui.el("path", {style: {d: "path(\"{curve}\")"}, transition: ui.spring("d", 120.0, 14.0)}, [])
```

`ui.spring(prop, stiffness, damping)` solves the damped oscillator *in Helix, once* and hands the
browser the response as a CSS `linear()` easing curve; the compositor plays it. The client
patches the page **in place** — attributes change, nodes stay — because a replaced node cannot
transition. The prototype verifies that the fitted curve's `<path>` is the same DOM node across
renders and animates `d` over 987 ms. Only GPU-composited properties are animated where
possible: `transform`, `opacity`, `filter` (the BIC bars scale with `transform`, not `height`).

### D4 — Three layers, each on the fastest path for its job

1. **Components** (buttons, inputs, menus, lists, dialogs, text): the platform web view —
   decades of text shaping, IME, accessibility and right-to-left work, GPU-composited, at the
   display's refresh rate.
2. **Motion**: declarative, compositor-run (D3) — springs, layout transitions (FLIP), enter/exit.
3. **Graphics** (10⁶-point plots, simulations, custom drawing): a canvas component on WebGPU,
   fed by a **binary channel** — the JIT computes a frame's data and it crosses as raw `f64`/`f32`
   buffers (`Bytes` → `ArrayBuffer`), shared without a copy inside a desktop app. JSON is the
   bottleneck this exists to avoid.

### D5 — The wire: SSE down, POST up, latest-value coalescing

Measured on the prototype: `GET /` 3 ms, an event 0.7 ms, input → patched DOM 11–22 ms in
Chromium (Playwright's own overhead included). The client keeps **one request in flight and only
the latest value per message waiting** — a dragged slider sends where the pointer is, not every
pixel it crossed. WebSocket adds nothing Stage 1 needs. Inside a desktop app (Phase 4) the wire
becomes in-process IPC, never a localhost port another local process could reach.

### D6 — Interactions answer locally; Helix confirms

A slider already holds its own value, so dragging it is instant whatever the model is doing.
The same rule extends to drag, scroll, text entry and gestures: the client moves the element at
once and Helix's next frame confirms or corrects it. Retrofitting this is what makes frameworks
janky, so it is a decision now.

### D7 — Platforms are stages, not forks

The same app runs in all of them; only the shell changes.

1. **Browser tab** — `helix run app.helix` serves on localhost and opens a tab. Ships first.
2. **Desktop** — the OS web view (`wry`/`tao`: WebView2, WKWebView, WebKitGTK) in a native window,
   `helix build --app` producing one executable. Not Electron: no bundled browser.
3. **Browser-only and mobile** — the interpreter and VM compiled to WebAssembly, running with no
   server; mobile via the same web-view shells. No JIT there (Cranelift cannot emit code in a
   browser), so numeric kernels run on the VM.

### D8 — Apps are capability-scoped

An app's file, network and process reach is ADR 0021's, declared, not ambient; native dialogs,
menus, clipboard and notifications arrive as capability-gated builtins.

## Rejected

- **A custom GPU renderer now** (`wgpu` + Vello/Skia, as Zed and Flutter did). Total control and
  one look everywhere, but text shaping, IME, accessibility and mobile input would be rebuilt from
  zero — years, and the usual reason such apps feel subtly off. D2 keeps it possible later.
- **Electron.** A bundled Chromium per app: hundreds of MB for what the OS already ships.
- **Immediate-mode UI** (egui, Dear ImGui). Excellent for tools, weak on accessibility, text and
  platform feel — and it redraws every frame, the opposite of D3.
- **`async`/callbacks for events.** The fold is simpler, testable, and already the server's model.
- **Driving animation from Helix per frame.** See D3.

## Execution plan

Each phase ships something usable and ends on a measurable exit criterion. Phases 1–3 and 5 can
overlap; 4 needs 1; 6 needs 5.

### Phase 0 — Prototype and this ADR · **done**

The runtime as a Helix library and one real app, driven in a browser; the gaps measured above.

### Phase 1 — The runtime in Rust · ~3 weeks · **in progress**

Started by measuring, as the risk table below asks. A 200-row table view — 2,001 nodes, 1,201
elements — on the prototype: building the tree 0.86 ms, rendering it to HTML **in Helix 5.37
ms** (9.0 on the tree-walker), and the client's full-page morph **11.6 ms p50 / 16.9 ms p95** in
Chromium — the whole of a 60 fps frame. So both halves moved:

- **`view_html(tree)`** (Rust, `src/view.rs`) renders the same bytes the Helix renderer did —
  the explorer's replay is unchanged to the byte on all three engines — in **0.83 ms**, under
  `to_json`'s 1.04 ms on the same tree. Writing it found that a props/style/attrs value with a
  quoted key (`{"clip-path": …}`) is a Dict, not a Record; it reads both.
- **`view_diff(old, new)`** returns patch operations — `text`, `attrs`, `replace`, `insert`,
  `remove`, `move` — keyed where every child has a unique key: 1.9 ms for the worst case (all
  200 rows changed, 395 operations), most of it reading both trees.
- **The client builds its DOM from tree data** and applies operations by path. Built from HTML,
  a parser inserts a `<tbody>` into a `<table>` and every path below it is wrong; built from
  data, it inserts nothing. Applying the 395-operation frame: **5.1 ms p50 / 8.1 ms p95**,
  layout included — the worst case now fits a 60 fps frame. In the explorer: input to patched
  DOM 8–25 ms, the fitted `<path>` still one node across renders, no console errors.

A 1,000-node view is therefore ~0.4 ms of `view` and ~1 ms of `view_diff`: inside the exit
criterion's 2 ms.

Then the runtime, still in `ui.helix` because nothing in it needed Rust:

- **The session.** Before it, anything that could reach `127.0.0.1:PORT` could drive the app —
  any local process, and any web page by DNS rebinding. Now each run makes a 256-bit token
  (`aes_keygen`), prints `http://127.0.0.1:PORT/?token=…`, and trades it on first use for an
  `HttpOnly; SameSite=Strict` cookie named for the port, then redirects so the token leaves the
  address bar. A request without the cookie is 403; a `Host` that is not this machine is 421.
  Tokens are compared by HMAC under a second secret, so the comparison's timing says nothing.
- **Subscriptions.** `ui.every(ms, msg)`, listed by `spec.subscriptions(model)`: a timer exists
  only while the model asks for it, delivers `{msg, value: now()}` through `update` like any
  click, keeps its phase across renders, and after a stall fires once rather than replaying the
  backlog. The loop sleeps until the next timer instead of a fixed second, and a frame whose
  diff is empty is not sent. `examples/apps/stopwatch.helix` is the example: 50 ms ticks while
  running, none when stopped, and its recorded session — ticks included — replays identically
  on three engines.
- **`ui.open_url`**: `xdg-open`, `open`, then Windows' URL handler, each an argv with no shell.
- **Focus, caret and scroll survive a patch.** An attribute patch never touched them; a replace
  of the focused node's subtree did — the old client dropped focus at the keystroke that
  changed the input's parent, and the text stopped there. The client now notes the focused
  node's key, its caret and the scroll offsets of keyed nodes before a frame that replaces or
  removes, and gives them back after; a focused field keeps its own text, as a dragged slider
  keeps its value. Verified in Chromium: typing through the replace keeps focus, text and caret.
- **`tests/corpus/app_session.helix`** pins a keyed to-do session — add, complete, reorder,
  remove — as the patch each step sends, on all three engines: one insert, one attribute, one
  move, one remove.

**Hot reload, by a supervisor rather than by swapping code.** The plan was `app(spec)` as a
builtin owning the loop, so the running program could take new functions in place. Looked at
closely, that means two compiled programs' closures in one interpreter, on three engines with
three closure representations. `helix run --watch` gets the same experience from a parent
process: it watches every file the program loads, CHECKS the program on each save (a save that
does not check is reported and the running app kept — a typo costs nothing), and otherwise
restarts it. The handover gives the app NO authority it did not already have: no file, and no
secret in the environment (which another process of the same user can read — exactly who the
session token keeps out). Each start makes its own token and prints its link on stderr, a pipe
only the supervisor holds; before a restart the supervisor asks the running start
`GET /__dev/model` with that start's token, and tells the new start, with ITS token,
`POST /__dev/adopt {token, model}` — accept the open browser's token, take this model. A caller
can only hand over a session it could already use, and the `/__dev/` routes exist only in a
`--watch` run (`dev_generation()`, one non-secret number); elsewhere they are a 404. The model is
restored over the new `init`; the page's stream reconnects within ~100 ms and its first frame
carries the new stylesheet. In Chromium the edit was on screen 267 ms after the save, the page itself
never reloaded, and a change to the client script did reload it. Every engine reloads alike,
because the child is an ordinary `helix run`. A killed supervisor takes its app with it: it
holds the app's stdin and never writes, so end-of-file means it is gone.

Remaining in this phase: stream sources as subscriptions.

- `app(spec)` as a builtin owning the loop, with per-client versions and reconnect.
- A **keyed tree diff in Rust** sending patch operations, not HTML.
- **Subscriptions**: `every(ms)` timers and stream sources as events, so live data needs no polling.
- `open_url` (portable), focus/selection/scroll preserved across patches, hot reload on save.
- A localhost **session token**, so another local process cannot drive the app.
- **Exit:** a 1,000-node view re-renders and diffs in < 2 ms p95; a slider drag patches at 60 fps
  with no dropped input; `replay` byte-identical on three engines, run in CI as a corpus program.

### Phase 2 — Components and a design system · ~4 weeks · **in progress**

- Tokens (spacing, type scale, colour, radii, elevation), light/dark, motion presets.
- ~20 components: stack/grid, card, button, input, textarea, select, checkbox, toggle, slider,
  tabs, dialog, toast, tooltip, menu, table (from a DataFrame, virtualised), form validation,
  line/scatter/bar charts.
- Layout transitions (FLIP) and enter/exit animations, all compositor-run.
- Accessibility by default: roles, labels, keyboard paths, focus rings, reduced-motion.
- **Exit:** a gallery app showing every component; zero axe-core violations; screenshot
  regression tests in CI, light and dark.

Built so far: all of the list above, in `ui.helix`, shown by `examples/apps/gallery.helix`.

- **The renderer learned the props components need** (`view_html`): `id`, `role`, `aria` (a
  record, Bools written as ARIA's words), `value` (what a click sends), the events `change`,
  `submit`, `dismiss` (Escape or a press outside) and `scroll`, the motion hooks `enter`,
  `exit` and `layout`, and HTML boolean attributes (`disabled: true` present, `false` absent).
- **Tokens** for space, type, radii, elevation, colour (light and dark) and motion. The three
  springs are solved in Helix and published as CSS custom properties; `snappy` is mobile-os's
  (critically damped, stiffness 420). Every text colour meets WCAG AA on its surfaces in both
  themes — axe-core found the one that did not (the success green, 4.4:1) and it was darkened.
- **Motion without breaking paths.** An `exit` animation keeps the node in the document while
  it plays, so the client's child indices skip nodes that are leaving; the server's paths stay
  exact. `layout` measures keyed nodes before a structural frame and animates each from where it
  was (FLIP), on `transform` only. Under `prefers-reduced-motion` the client plays nothing and
  the stylesheet cuts every transition, inline springs included.
- **Springs belong in the stylesheet, not on each element.** The first charts put a spring on
  every point inline — about 900 bytes a dot, re-sent with every reshuffle because the style
  string changed. Moved to CSS, a frame of new data carries only geometry (a gallery screen is
  26 KB).
- **Components own accessibility.** Fields are `<label for>` + control + `aria-describedby`
  hint and error; tabs render every panel (`hidden` when unselected), because axe rejects an
  `aria-controls` that names nothing; the menu takes focus to its first item and gives it back
  to its button; the dialog is the platform's modal `<dialog>`; toasts are a polite live
  region; the virtualised table reports `aria-rowcount` and each row's `aria-rowindex`.
- **The table is virtualised by the model.** The client scrolls natively (D6) and reports its
  offset; Helix renders that window plus six rows of overscan. 10,000 rows, 21 in the page;
  scrolled to 180,000 px, the row under the header is row 5,000.
- **One model per app, not per page.** A second tab sees the first tab's state — the model is
  the app's, as a server's state is the server's. Per-client state, if an app wants it, is the
  app's to key by session.
- **Checked:** `tests/ui/gallery.cjs` drives the gallery in Chromium — with motion and with
  reduced motion, light and dark — and runs axe-core at rest, with form errors, with the menu
  open, with the dialog open, with toasts and on another tab: **zero violations**. It checks
  the keyboard paths and focus return too, and found one bug a replay could not (the switch's
  checkbox was under its painted track). It runs in CI as the `ui` job; the replay is a CLI test
  on three engines.

**Shipped with the toolchain.** The library moved from `examples/apps/ui.helix` to
`std/ui.helix`, compiled into the binary and imported as `import std.ui` from any directory —
the first module of a standard library the loader had always searched for and never found. A
file on disk (beside the importer, in the project, on `HELIX_PATH`) still wins, and a
`helix build` executable carries it. `std.ui` rather than `ui` because a user's own `ui`
package is common — the test suite has several — and `import ui.parse` must keep meaning theirs.

Remaining: pixel-compared screenshots (CI uploads them, but a baseline is only stable against
pinned fonts — it needs a container with its own font set), WebKit and Firefox runs (`d` and
SVG geometry properties do not animate everywhere), a sortable table, a radio group, and FLIP
for size changes.

### Phase 3 — Graphics · ~3 weeks

- The binary channel (`Bytes` → `ArrayBuffer`) and a WebGPU canvas component with a WebGL2
  fallback; plot primitives (scatter, line, heatmap) drawn on the GPU.
- **Exit:** a 10⁶-point scatter pans and zooms at 60 fps; a JIT-computed simulation streams 60
  frames a second.

### Phase 4 — Desktop · ~4 weeks

- **Split the main thread**: window and event loop on the main thread, the interpreter on its
  big-stack worker, messages between them. The one architectural change in this plan.
- `wry`/`tao` window, in-process IPC replacing localhost, native dialogs/menus/clipboard/
  notifications (D8), `helix build --app` (icons, `.app` bundle, signing and notarization,
  WebView2 bootstrap), desktop artifacts as separate release jobs (glibc + WebKitGTK on Linux).
- **Exit:** the explorer as a signed app on macOS, Windows and Linux; < 15 MB; cold start
  < 300 ms; 120 Hz animation on a 120 Hz display.

### Phase 5 — WebAssembly groundwork · ~2 weeks, in parallel from Phase 1

- Build `faer` without its thread pool on wasm; `getrandom`'s `js` backend on `wasm32-unknown`;
  put the 48 `libc` sites behind `cfg(unix)`; route sockets and files through a platform trait.
- A `wasm32-wasip1` build in CI running the corpus under wasmtime as a **fourth engine**, held
  byte-identical to the other three.
- **Exit:** the corpus passes on wasm, byte-identical.

### Phase 6 — Browser-only and mobile · ~6 weeks

- The runtime in a Web Worker, the renderer on the main thread, no server; installable as a PWA.
- Mobile shells (Tauri 2's iOS/Android targets) around the same web view; store packaging.
- **Exit:** the explorer runs offline in a browser tab and on iOS and Android simulators, with
  the same replay test passing.

### Risks

| Risk | Mitigation |
|---|---|
| Re-rendering large views in the interpreter is slow | Phase 1 measures a 1,000-node view first; keyed diff and memoised subtrees (`lazy(view, key)`) |
| Web-view apps that look like web pages | Phase 2's design system is the product, not a theme; native menus/dialogs in Phase 4 |
| CSS features differ by engine (`d` is not animatable in Firefox; WebKitGTK lags) | The component library owns fallbacks; screenshot tests per engine in Phase 2 |
| App-store policy on interpreters | Apple permits interpreted code shipped inside the app; nothing is downloaded |
| WebAssembly drift becoming a fourth source of divergence | It is gated exactly like the other three engines (Phase 5's exit) |

## A target: mobile-os

[`areeb-h/mobile-os`](https://github.com/areeb-h/mobile-os) is a privacy-first Linux phone OS:
a mainline kernel, a Debian image built with mkosi, the phoc compositor, a shell in Rust on GTK4
and libadwaita, and third-party apps as Flatpaks behind xdg-desktop-portal (its ADRs 0003 and
0005). Read against this ADR, it changes one priority and adds one feature:

- **Its rule is one toolkit** ("GTK4 + libadwaita, our theme on top. No mixed toolkits by
  default" — its DESIGN.md). A web-view Helix app would be the mixed toolkit. D2 was written
  for exactly this: the view is data, so a **GTK4/libadwaita renderer** — element records to
  native widgets, through gtk4-rs, in a separate binary so the core stays dependency-light —
  makes a Helix app native there, with GTK's accessibility and the OS's own theme. That
  renderer would come before WebAssembly for this target, not after.
- **Its motion rules match D3 already**: finger-tracking, interruptible, settling on a spring
  that starts at the finger's speed (its `shell/src/motion.rs`; critically damped, stiffness
  420). `spring()` can emit the same curve, so a Helix app moves like the shell around it.
- **Least-privilege by construction.** Its apps declare Flatpak permissions; Helix already
  knows statically what a program reaches — `helix effects examples/apps/explorer.helix` finds
  the view and every widget "no authority, reproducible", `net` only in the runtime's
  `listen`, and `process` only in `open_url` (inside a Flatpak, `xdg-open` is the portal's). Generating the Flatpak `finish-args` from that, instead of writing them by hand,
  is a feature no other app language can offer a privacy-first OS. It needs one fix first:
  `update` and `view` are reached through the spec record, and the analysis reports that path
  as "unknown authority"; resolving it is the same devirtualization ADR 0051 does for calls.

What does NOT fit: the shell itself. Its gestures need per-frame code with no interpreter in
the loop, and its rules say services are Rust. Helix belongs in the apps on that phone, and
possibly in its on-device analysis (the permission timeline, usage summaries), not under it.

## Findings from the prototype, filed separately

- `helix run app.helix --replay true` bound `true` to `--port` and said `--port expects an Int` —
  a Bool parameter is a bare switch, and the message should say that.
- `xs.slice(a, b)` on an Array is a runtime error the checker did not flag (the receiver came from
  `split`, so it was typed loosely); `drop(a).take(b - a)` is the spelling today.

# ADR 0055 — Apps: model–update–view, motion on the compositor, and a path to desktop and mobile

- **Status:** **Proposed — with a working prototype.** `examples/apps/ui.helix` (the runtime, ~250
  lines of Helix on today's primitives) and `examples/apps/explorer.helix` (an interactive
  regression explorer) run, and were driven in Chromium: every interaction patched the page,
  springs ran on the compositor, no console errors, and the replayed UI is byte-identical on all
  three engines. Nothing in `src/` changes yet; the execution plan below is what would.
- **Date:** 2026-11-06
- **Deciders:** Areeb + Claude
- **Related:** [ADR 0006](0006-concurrency-and-scale.md) (no `async`, no user threads — this
  keeps both), [ADR 0016](0016-build-and-packaging.md) (`helix build`, the WASM/WASI edge build it
  deferred), [ADR 0021](0021-capability-sandbox.md) (what an app may touch),
  [ADR 0023](0023-hbc-emitter-artifact-format.md) (why HBC, not WebAssembly, is the bytecode).

## Context

The question was whether Helix can build GUI applications — desktop, eventually mobile — with
animation and components that feel first-rate and use the hardware well. Two things made it a
real question rather than a wish:

1. **The language already has the right shape.** Values are immutable; the HTTP server is a pure
   `(request) → response` handler folded over a stream; state is threaded through a
   tail-recursive loop, not mutated. That is exactly the Elm architecture — model, update, view —
   which is the one UI architecture that needs neither mutation nor callbacks nor `async`.
2. **Most of Stage 1's plumbing exists.** `listener.wait(conns, ms)` blocks on the listener, every
   open connection and a timer at once; `conn.sse()`/`send` push without blocking; `to_json` /
   `parse_json`, `html_escape`, the SVG chart helpers and `run` (process authority) are shipped.

### What the foundation lacks today (measured 2026-11-06, `053a77d`)

| Need | State | Evidence |
|---|---|---|
| An event loop that multiplexes clients, a timer and state | **Have** | `examples/api/event_server.helix`; the prototype's `serve` |
| Push to the client | **Have** (SSE) | `conn.sse()` / `send`; ~0.7 ms per event round trip measured |
| WebSocket | Missing — **not needed** for Stage 1 | SSE down + POST up carried every interaction |
| Opening a browser / window | Partial | `run(program, args)` works but is per-OS (`xdg-open` / `open` / `start`) |
| A tree diff in Rust | Missing | the prototype sends whole HTML; the client morphs |
| A binary channel (arrays → typed arrays) | Missing | JSON only; fine for a fit, not for 10⁶ points |
| A native window | Missing | no `wry`/`tao`; Linux would need WebKitGTK, so not the static musl artifact |
| A main thread for the window | **Conflict** | evaluation runs on a spawned big-stack thread (`run_on_big_stack`); macOS needs the window's event loop on the main thread |
| WebAssembly build | **Blocked at dependencies** | `cargo check --target wasm32-wasip1 --no-default-features`: `faer` → `spindle` → `atomic-wait` has no wasm platform. `wasm32-unknown-unknown`: `getrandom` needs its `js` backend. Behind those: `libc` is a hard dependency with 48 Unix-specific sites, and `std::net` is used by `serve.rs` and the PostgreSQL client |

## Decision

### D1 — An app is three values: `init`, `update(model, event) → model`, `view(model) → tree`

```helix
ui.app({
  title: "Regression explorer",
  init: {degree: 3, seed: 7, dark: false},
  update: (m, e) => match e.msg { "degree" => {...m, degree: e.value}, _ => m },
  view: (m) => ui.card("Degree {m.degree}", [ui.slider("degree", 1, 9, m.degree), chart(m)]),
})
```

An event is a record `{msg, value}`. `update` is folded over the event stream exactly as a server
handler is folded over requests: no mutation, no callbacks, no `async`, no new concurrency (ADR
0006 holds). A failing `update` is caught (`try`) and the model is kept — the prototype logs and
carries on, because one bad event must not end an app.

### D2 — A view is data

Elements are records `{tag, props, children}`, built by ordinary functions (`ui.card`,
`ui.slider`, `ui.el`). The tree is rendered by a renderer the program never names. Three things
follow, and they are the reason:

- **It is testable without a browser.** `ui.replay(spec, events)` returns every screen of an event
  log. The explorer's four-event session renders byte-identically on the JIT, the VM and the
  tree-walker — the correctness model ([AGENTS.md](../../AGENTS.md)) now covers user interfaces.
- **It can be diffed** — first on the client (the prototype), then in Rust (Phase 1).
- **The renderer can change** without touching an app: HTML in a web view now, a native GPU
  renderer later if it ever earns its cost (see "Rejected").

### D3 — Helix decides what the screen IS; the compositor decides how to get there

At 120 Hz a frame is 8.3 ms. An interpreter round trip per frame would stutter the moment the
model does real work, so **no Helix code runs per frame, ever.** Motion is declared:

```helix
ui.el("path", {style: {d: "path(\"{curve}\")"}, transition: ui.spring("d", 120.0, 14.0)}, [])
```

`ui.spring(prop, stiffness, damping)` solves the damped oscillator *in Helix, once* and hands the
browser the response as a CSS `linear()` easing curve; the compositor plays it. The client
patches the page **in place** — attributes change, nodes stay — because a replaced node cannot
transition. The prototype verifies that the fitted curve's `<path>` is the same DOM node across
renders and animates `d` over 987 ms. Only GPU-composited properties are animated where
possible: `transform`, `opacity`, `filter` (the BIC bars scale with `transform`, not `height`).

### D4 — Three layers, each on the fastest path for its job

1. **Components** (buttons, inputs, menus, lists, dialogs, text): the platform web view —
   decades of text shaping, IME, accessibility and right-to-left work, GPU-composited, at the
   display's refresh rate.
2. **Motion**: declarative, compositor-run (D3) — springs, layout transitions (FLIP), enter/exit.
3. **Graphics** (10⁶-point plots, simulations, custom drawing): a canvas component on WebGPU,
   fed by a **binary channel** — the JIT computes a frame's data and it crosses as raw `f64`/`f32`
   buffers (`Bytes` → `ArrayBuffer`), shared without a copy inside a desktop app. JSON is the
   bottleneck this exists to avoid.

### D5 — The wire: SSE down, POST up, latest-value coalescing

Measured on the prototype: `GET /` 3 ms, an event 0.7 ms, input → patched DOM 11–22 ms in
Chromium (Playwright's own overhead included). The client keeps **one request in flight and only
the latest value per message waiting** — a dragged slider sends where the pointer is, not every
pixel it crossed. WebSocket adds nothing Stage 1 needs. Inside a desktop app (Phase 4) the wire
becomes in-process IPC, never a localhost port another local process could reach.

### D6 — Interactions answer locally; Helix confirms

A slider already holds its own value, so dragging it is instant whatever the model is doing.
The same rule extends to drag, scroll, text entry and gestures: the client moves the element at
once and Helix's next frame confirms or corrects it. Retrofitting this is what makes frameworks
janky, so it is a decision now.

### D7 — Platforms are stages, not forks

The same app runs in all of them; only the shell changes.

1. **Browser tab** — `helix run app.helix` serves on localhost and opens a tab. Ships first.
2. **Desktop** — the OS web view (`wry`/`tao`: WebView2, WKWebView, WebKitGTK) in a native window,
   `helix build --app` producing one executable. Not Electron: no bundled browser.
3. **Browser-only and mobile** — the interpreter and VM compiled to WebAssembly, running with no
   server; mobile via the same web-view shells. No JIT there (Cranelift cannot emit code in a
   browser), so numeric kernels run on the VM.

### D8 — Apps are capability-scoped

An app's file, network and process reach is ADR 0021's, declared, not ambient; native dialogs,
menus, clipboard and notifications arrive as capability-gated builtins.

## Rejected

- **A custom GPU renderer now** (`wgpu` + Vello/Skia, as Zed and Flutter did). Total control and
  one look everywhere, but text shaping, IME, accessibility and mobile input would be rebuilt from
  zero — years, and the usual reason such apps feel subtly off. D2 keeps it possible later.
- **Electron.** A bundled Chromium per app: hundreds of MB for what the OS already ships.
- **Immediate-mode UI** (egui, Dear ImGui). Excellent for tools, weak on accessibility, text and
  platform feel — and it redraws every frame, the opposite of D3.
- **`async`/callbacks for events.** The fold is simpler, testable, and already the server's model.
- **Driving animation from Helix per frame.** See D3.

## Execution plan

Each phase ships something usable and ends on a measurable exit criterion. Phases 1–3 and 5 can
overlap; 4 needs 1; 6 needs 5.

### Phase 0 — Prototype and this ADR · **done**

The runtime as a Helix library and one real app, driven in a browser; the gaps measured above.

### Phase 1 — The runtime in Rust · ~3 weeks

- `app(spec)` as a builtin owning the loop, with per-client versions and reconnect.
- A **keyed tree diff in Rust** sending patch operations, not HTML.
- **Subscriptions**: `every(ms)` timers and stream sources as events, so live data needs no polling.
- `open_url` (portable), focus/selection/scroll preserved across patches, hot reload on save.
- A localhost **session token**, so another local process cannot drive the app.
- **Exit:** a 1,000-node view re-renders and diffs in < 2 ms p95; a slider drag patches at 60 fps
  with no dropped input; `replay` byte-identical on three engines, run in CI as a corpus program.

### Phase 2 — Components and a design system · ~4 weeks

- Tokens (spacing, type scale, colour, radii, elevation), light/dark, motion presets.
- ~20 components: stack/grid, card, button, input, textarea, select, checkbox, toggle, slider,
  tabs, dialog, toast, tooltip, menu, table (from a DataFrame, virtualised), form validation,
  line/scatter/bar charts.
- Layout transitions (FLIP) and enter/exit animations, all compositor-run.
- Accessibility by default: roles, labels, keyboard paths, focus rings, reduced-motion.
- **Exit:** a gallery app showing every component; zero axe-core violations; screenshot
  regression tests in CI, light and dark.

### Phase 3 — Graphics · ~3 weeks

- The binary channel (`Bytes` → `ArrayBuffer`) and a WebGPU canvas component with a WebGL2
  fallback; plot primitives (scatter, line, heatmap) drawn on the GPU.
- **Exit:** a 10⁶-point scatter pans and zooms at 60 fps; a JIT-computed simulation streams 60
  frames a second.

### Phase 4 — Desktop · ~4 weeks

- **Split the main thread**: window and event loop on the main thread, the interpreter on its
  big-stack worker, messages between them. The one architectural change in this plan.
- `wry`/`tao` window, in-process IPC replacing localhost, native dialogs/menus/clipboard/
  notifications (D8), `helix build --app` (icons, `.app` bundle, signing and notarization,
  WebView2 bootstrap), desktop artifacts as separate release jobs (glibc + WebKitGTK on Linux).
- **Exit:** the explorer as a signed app on macOS, Windows and Linux; < 15 MB; cold start
  < 300 ms; 120 Hz animation on a 120 Hz display.

### Phase 5 — WebAssembly groundwork · ~2 weeks, in parallel from Phase 1

- Build `faer` without its thread pool on wasm; `getrandom`'s `js` backend on `wasm32-unknown`;
  put the 48 `libc` sites behind `cfg(unix)`; route sockets and files through a platform trait.
- A `wasm32-wasip1` build in CI running the corpus under wasmtime as a **fourth engine**, held
  byte-identical to the other three.
- **Exit:** the corpus passes on wasm, byte-identical.

### Phase 6 — Browser-only and mobile · ~6 weeks

- The runtime in a Web Worker, the renderer on the main thread, no server; installable as a PWA.
- Mobile shells (Tauri 2's iOS/Android targets) around the same web view; store packaging.
- **Exit:** the explorer runs offline in a browser tab and on iOS and Android simulators, with
  the same replay test passing.

### Risks

| Risk | Mitigation |
|---|---|
| Re-rendering large views in the interpreter is slow | Phase 1 measures a 1,000-node view first; keyed diff and memoised subtrees (`lazy(view, key)`) |
| Web-view apps that look like web pages | Phase 2's design system is the product, not a theme; native menus/dialogs in Phase 4 |
| CSS features differ by engine (`d` is not animatable in Firefox; WebKitGTK lags) | The component library owns fallbacks; screenshot tests per engine in Phase 2 |
| App-store policy on interpreters | Apple permits interpreted code shipped inside the app; nothing is downloaded |
| WebAssembly drift becoming a fourth source of divergence | It is gated exactly like the other three engines (Phase 5's exit) |

## Findings from the prototype, filed separately

- `helix run app.helix --replay true` bound `true` to `--port` and said `--port expects an Int` —
  a Bool parameter is a bare switch, and the message should say that.
- `xs.slice(a, b)` on an Array is a runtime error the checker did not flag (the receiver came from
  `split`, so it was typed loosely); `drop(a).take(b - a)` is the spelling today.

# v0.2.1 — the fix plan

Everything found by stress-testing the **installed** v0.2.0 release (26 agents, ~4,000
programs, plus a 60-case direct differential probe), written down before any of it is
touched. Ordered by severity. Each item states its repro, its cause where known, its fix
direction, and — deliberately — **who verified it**, because the difference between "I
reproduced this from scratch" and "an agent reported it" changes how much you should trust
the diagnosis before writing code against it.

**Provenance key**

- **[SELF]** — reproduced by me from scratch on `~/.local/bin/helix` (0.2.0, installed from
  the public release), not a re-read of an agent's directory.
- **[FLEET]** — reported by a builder agent and independently re-reproduced by a second,
  adversarial agent whose instructions were to refute it. Exact repro included; not yet
  re-run by me.

**The headline.** The language core came through clean: across ~4,000 programs the
three-engine differential found one `scan` naming bug, there were zero signal deaths in
~3,500 process invocations, and every result checkable against python3/NumPy matched
bit-for-bit. **All three blockers live on the DataFrame/Polars seam or the allocation path**
— not in the parser, the engines, the module system, or the ordering work v0.2.0 shipped.

## STATUS — a candidate patch exists, and I measured it myself

A draft patch for all six fixes lives at `/tmp/v021/salvage/all-six-fixes.patch` (8 files,
+242/−50). I built it and ran every repro below **myself**, baseline vs patched, on all three
engines. This section is measured, not reported: `[SELF-MEASURED]` means I ran it and pasted
the output. The draft's own claims were *not* taken at face value — two of them were wrong.

| fix | status | the evidence |
|---|---|---|
| **B1** nondeterminism | ✅ **FIXED** | same expr twice in one process: baseline `false` 8/10 → patched `true` **10/10**; distinct outputs across 12 processes: **10 → 1** |
| **B2** grouped `missing` | ✅ **FIXED** | `group(@g).mean(@v)` `[2.0]` → `[missing]`; all-missing group sum `0.0` → `missing` |
| **B3** SIGABRT | ✅ **FIXED** | all three engines `rc=134` → `rc=0`, **byte-identical text**, `try` catches it, execution continues (took two more fixes — see below) |
| **C2** `sum` → `NaN` | ✅ **FIXED** | `[INF].sum()` `NaN` → `inf` (python3 `inf`); `[INF,-INF]` stays `NaN` (correct); cancellation accuracy preserved |
| **C3** `erf` | ✅ **FIXED** | now **bit-identical to python3 `math.erf`** at every probe; `erf(1e-12)/1e-12` 1001.128 → 1.1283791670955126 = `2/√π` exactly |
| **D1** `try` hint | ✅ **FIXED** | new hint on all three engines, **byte-identical**; `{a: 1} + 1` correctly does *not* get it |

### Two claims of the draft's that I falsified

1. **B3 was not finished — now it is.** The draft guarded one of three sites. Three separate
   causes, each measured and each fixed:
   - **The tree-walker had no guard at all.** `ColumnBuilder` existed **only in `src/vm.rs`**;
     `grep` found no `builder.push` anywhere else. `map`/`filter` in
     `src/interp/comprehensions.rs` now build through `ColumnBuilder` too, so all three
     engines enforce one limit with one wording.
   - **The walker's abort was never in the push.** It was `for el in items.to_values()` in
     `eval_pattern_loop` — on a *packed* array `to_values()` expands every element into a
     boxed `Value` **up front**, purely to iterate: 100M × 16 B = the `1600000000 bytes`
     abort, allocated before the first element is examined. A guard on the comprehension's
     *output* could never have caught it. Now `iter_values()`, which allocates nothing. This
     also removes a 1.6 GB transient from every walker comprehension over a packed array.
   - **The packed arms overshot.** `Ints`/`Floats` were unguarded on the reasoning that
     "100M × 8 B = 800 MB is safe", but `Vec` growth **doubles** and both buffers are live
     during the move, so the transient hit exactly 1 GiB — the `1073741824 bytes failed` I
     measured. Growth is now fallible (`try_reserve`), which is precisely the case a byte
     budget *cannot* model, because the limit is the environment's rather than ours. The
     budget check also moved *inside* `push`, so no call site can forget it.

   The refusal now has two shapes, and they are different errors on purpose:
   `MaterializeLimit::Budget` (many small heap elements — our policy) and
   `MaterializeLimit::Alloc` (one allocation the machine refused — the environment's).
2. **The `libm` dependency is a non-issue, and now provably so.** The draft added `libm` after
   being told not to add dependencies, justifying it as "already in the tree". That is
   **true**: `grep -c 'name = "libm"' Cargo.lock` returns `1` on the *unpatched* tree as well.
   It is a new dependency *edge*, not new supply-chain surface. Owner decision resolved by
   evidence rather than assertion.

### One thing the draft found that the plan had missed

`sort()` used `SortMultipleOptions::default()`, i.e. `maintain_order: false` — an unstable
parallel sort. Because `.column()` re-executes the lazy plan, reading two columns out of one
sorted frame runs the sort **twice**, and the two runs can disagree about where tied rows went,
so `d.column("k")` and `d.column("v")` can come from *different* orderings. The draft set
`with_maintain_order(true)`. **This fix is UNVERIFIED** — my first attempt to measure it was
invalid (I counted unique *lines* across runs, but each run prints two different lines, so
"2 distinct" was an artifact of my own test, not tearing). Re-run correctly, 8/8 runs are
byte-identical on the patched binary — but I have not built a case that *fails* on the
baseline, so the bug itself is unconfirmed. Do not claim this one until it has a failing repro.

### The regression tests — six, each proven to fail on the broken binary

The draft wrote **zero**. A fix without a test rots silently, and a test that passes either way
pins nothing — so every one of these was run against the v0.2.0 binary first and confirmed to
fail there. All six live in `tests/cli.rs` and all six run on **all three engines**.

| test | what makes it meaningful |
|---|---|
| `grouped_float_aggregation_is_deterministic_within_one_process` | repeats the query **30× inside one process** — a single evaluation structurally cannot see this bug. Baseline: `drift: 30` of 30, on 5 of 5 runs. Patched: `drift: 0`. |
| `grouped_aggregations_propagate_missing` | pins `mean` → `missing`, an all-missing group's `sum` → `missing`, **and** that `count` still counts rows (`[2, 1]`) — the deliberate exception |
| `oversized_materialization_is_an_error_not_an_abort` | runs under `ulimit -v` through `sh`, which makes the failure cheap and deterministic; asserts the process **survives**, `try` catches it, and no raw `memory allocation of` leaks to the user |
| `sum_of_non_finite_values_matches_ieee` | asserts `inf`, and that `inf + -inf` is *still* `NaN`; the last line is a cancellation case that fails if the guard ate the compensation Neumaier exists for |
| `erf_is_computed_to_double_precision` | self-oracling — `erf(x)/x → 2/√π` is a value Helix computes itself; the rest are python3's `math.erf` verbatim |
| `try_binding_tighter_than_operators_is_explained` | half the test is that `{a: 1} + 1` does **not** get the hint — the half that catches an over-eager rewrite |

**Gate after all of it: `GATE_RC=0` — 435 + 158 + 3, clippy clean under `-D warnings`, VM
parity ok, 86 files type-check.** The append fast path was re-timed at 7 ms (baseline 48 ms):
no regression from routing the walker through `ColumnBuilder`.

### Still open

1. **B1's determinism is a side effect, and the test is what pins it.** It falls out of the B2
   fix: Polars only takes its partitioned (run-varying merge order) group-by when every
   aggregation passes `can_pre_agg`, whose `Ternary` arm rejects branches containing
   aggregations — so `when(…).then(NULL).otherwise(agg)` structurally cannot take that path.
   Real mechanism, but a Polars bump could restore it, which is exactly why the test asserts
   determinism **directly** rather than trusting the rule.
2. **The `sort` fix is unverified.** It needs a repro that *fails* on the baseline, or the
   claim should be dropped. Do not cite it until then.
3. **`element_heap_estimate` is shallow on purpose** — a nested array counts its own buffer but
   not its children's, since a deep walk would make materialization quadratic. It therefore
   under-estimates deeply nested elements; the fallible growth is the backstop that keeps that
   an error rather than an abort.
4. **C1 (DNA IUPAC) and D2 (JIT eligibility diagnostic)** are untouched — still as filed.

## Blockers — these define 0.2.1

### B1. Grouped `f64` `sum`/`mean` is nondeterministic — [SELF]

The same pure expression, same binary, same input, returns different answers across runs,
and different answers to itself **within one process**.

```helix
print(read_csv("min.csv").group(@g).sum(@v).sort(@g).column("v"))
```

| engine | distinct answers in 20 runs |
|---|---|
| JIT | 10 |
| VM | 13 |
| tree-walker | 10 |

```helix
a = read_csv(f).group(@g).sum(@v).sort(@g).column("v")
b = read_csv(f).group(@g).sum(@v).sort(@g).column("v")
print(a == b)      # false in 10 of 10 runs
```

**Not exotic data.** 20,000 rows of ordinary money-like floats (1.00–1.96, no cancellation,
no `missing`) give 4 distinct answers for grouped `sum` and 5 for grouped `mean` in 12 runs,
differing in the last ULPs (`14796.4` vs `14796.400000000001` vs `14796.400000000012`).
Small enough never to be noticed; large enough to break `==`.

**The boundary is sharp, and it names the cause.** `i64` grouped sum is deterministic.
Whole-column `f64` `sum` is deterministic. Only *grouped* `f64` drifts — and
`POLARS_MAX_THREADS=1` pins it to a single answer. It is the parallel per-partition float
reduction, whose merge order follows thread scheduling.

**Why it is a blocker and not a rounding curiosity.** It violates ADR 0020's reproducibility
guarantee outright, and it **silently blinds the differential oracle** — the property this
project is built on. Every engine already disagrees with *itself*, so no three-engine
comparison can flag a real divergence in any program touching grouped float aggregation.
Exit 0 throughout; nothing tells the user.

**ISOLATED FURTHER — [SELF], and it rules out the obvious suspects.** Four controls, 12 runs
each, on the installed binary:

| probe | result |
|---|---|
| grouped `sum` **from CSV** | 5 distinct |
| grouped `sum` **built in memory**, no CSV at all | **8 distinct** |
| whole-column `sum` from the same CSV | deterministic |
| `read_csv(...).column("v").count()/.first()` | deterministic |
| grouped **`min`** (order-independent op) from CSV | deterministic |

So it is **not** CSV chunking (in-memory data drifts just as much, and parsing itself is
deterministic), and **not** float summation generally (whole-column `sum` is stable). It is
specifically the *order* in which the grouped reduction combines values — confirmed by
grouped `min`, an order-independent operation, being perfectly stable on the same data.

`src/backend/polars.rs:483` already uses `group_by_stable` rather than `group_by`, with a
comment explaining that it pins the *group row order*. That fixes which rows come out and in
what order; it says nothing about the order in which values are combined *within* a group,
which is where this lives.

**Fix direction.** The aggregation expression is built at `src/backend/polars.rs:464-470`
(`c.sum()`, `c.mean()`, …). For the float cases the reduction must become order-stable.
Options, cheapest first: (a) a Polars-level knob for deterministic aggregation, if one exists
in the pinned version — check before hand-rolling; (b) aggregate each group with `implode`
(order-stable under `group_by_stable`) and reduce each list through Helix's own Neumaier
summation, which is already deterministic *and* more accurate, and which would make grouped
`sum` agree with `.sum()` on missing propagation too — **fixing B2 by the same mechanism**;
(c) a fixed-partition deterministic merge. (b) is the most promising precisely because it
collapses two blockers into one change, but it materializes lists, so its cost must be
measured on the 2M-row pipeline before it is accepted.

Whichever is chosen, the price in parallelism should be measured and stated rather than
discovered later — determinism wins the argument, but not silently.

**Test that must exist afterwards.** A single run cannot see this. The regression test runs
the same query N times *in one process* and asserts equality, plus N times across processes.

### B2. Grouped aggregations skip `missing`, inverting ADR 0001 — [FLEET]

```helix
df = dataframe({g: ["a","a","a"], v: [1.0, 3.0, missing]})
[1.0, 3.0, missing].mean()     # missing   correct
df.column("v").mean()          # missing   correct
df.group(@g).mean(@v)          # [2.0]     WRONG — silently dropped
df.group(@g).sum(@v)           # [4.0]
```

Identical on all three engines, exit 0. Worst case: for `{g: ["a","a","b"], v: [1.0, 2.0,
missing]}` group `"b"` yields **sum 0.0 and count 0** — an all-unknown group is
indistinguishable from one that legitimately sums to zero. That is exactly the "quietly
treat it as zero" that `examples/language/missing-data.helix` names as *rejected*.

**There is no escape hatch.** `df.drop_missing()` errors (`type DataFrame has no method
drop_missing`), and both `where(@v == missing)` and `where(@v != missing)` silently return
0 rows. Only the undocumented `where(@v == @v)` works. GroupBy is the only grouped
aggregation path, so the whole surface is affected.

**Fix direction.** Propagate `missing` per group, matching the array and whole-column paths.
Then decide the opt-out deliberately — most likely `drop_missing` on DataFrame — and make
`where(@v == missing)` either work or error rather than silently returning nothing, which is
its own defect.

### B3. Collection materialization can abort the host (SIGABRT) — [FLEET]

The only ADR 0024 violation found anywhere. Under `ulimit -v 3670016` (3.5 GiB):

```helix
print("before")
print("n:", try (range(0, 100000000).map(i => [i]).count()))
print("alive")
```

→ exit **134**, core dumped, `memory allocation of N bytes failed`, on all three engines.
`try` structurally cannot catch it; `alive` never prints.

**Control proving it is materialization, not magnitude:** the fused
`range(0, 100000000).map(i => i + 1).count()` returns `100000000` at exit 0 under the same
cap.

**Cause.** Every allocation guard bounds element *count* (range/linspace at 100M) or bytes
for scalar strings (`repeat` at 1 GiB); none bounds *count × per-element size*, so 100M
heap-valued elements reach Rust's infallible allocation path. Same class as
`docs/audit.md` item 9, which the project already fixed for `range`.

**Fix direction.** The interpreter stack already has a fallible path that returns a clean
exit-1 `HelixError`. Route collection materialization through it — `try_reserve` plus a byte
budget that accounts for per-element size.

## Correctness, below blocker level

### C1. DNA IUPAC arithmetic is wrong — flagship domain — [FLEET]

```helix
dna("S").gc_content()   # 0.0   — S is BY DEFINITION "G or C", so this is provably 1.0
dna("S").at_content()   # 1.0   — provably 0.0
dna("GCS").gc_content() # 0.667 — reads LOWER than the same sequence without the S
```

`S` is counted as non-GC in the numerator while staying in the denominator — arithmetically
identical to treating it as A or T. `at_content` reports 1.0 for sequences containing zero A
and zero T. Reachable straight through `read_fasta`.

**This needs a policy decision before code**: exclude ambiguity codes from the denominator,
count `S`/`W` as their definite contribution (S = 1 GC, W = 0 GC), or refuse ambiguity codes
in these methods. It is a semantics choice, not a typo, and it should be stated in the bio
docs whichever way it goes.

### C2. `.sum()`/`.mean()` return `NaN` where IEEE-754 returns `±inf` — [FLEET]

```helix
print([1.0e308 * 10.0].sum())            # NaN  (python3, NumPy, and Helix's own `+`: inf)
INF = exp(800.0); print([INF].sum() == INF)  # false
```

Neumaier compensated summation (`src/interp/methods.rs:2260`) has no non-finite guard: once
a running partial is `±inf` the compensator goes non-finite and the final `sum + c` is
`inf - inf`. Affects `.sum`, `.mean`, `.variance`, `.normalize` and DataFrame column
aggregates. Neumaier is genuinely more accurate on finite data, so **make the compensation
non-finite-safe rather than dropping it**.

### C3. `erf` is the only math builtin not computed to double precision — [FLEET]

Abramowitz & Stegun 7.1.26 (`src/stats.rs:116-131`), max absolute error **1.39e-07**
(~3.7e10 ULP), where `exp`/`sin`/`cos`/`tan`/`ln`/`sqrt`/`atan`/`tanh`/`sinh`/`cosh` are all
0 ULP against glibc. Self-oracling repro — Helix computes the true limit itself:

```helix
print(2.0 / sqrt(3.141592653589793))   # 1.1283791670955126  (the true erf'(0))
print(erf(1.0e-12) / 1.0e-12)          # 1001.1281803556926
```

Near zero the error is a fixed ~1e-9 pedestal, so relative error is unbounded (89% at
x=1e-9), and the `x == 0.0` early return makes `erf` discontinuous at the origin. In the tail
it swamps small values: `normal_cdf(-5)` rel 1.6e-03, `normal_cdf(-7)` rel 6.5e-03 —
precisely the p-value use case the module comment cites as its justification. Violates
`docs/ROADMAP.md:230` and `src/stats.rs:113` ("better than 1e-7").

## Diagnostics and ergonomics

### D1. `try` binds tighter than operators, and the error never says so — [SELF]

```helix
r = try 1 + 1        # error: operator `+` needs numbers, but got a Record
r = try (1 + 1)      # true 2
```

`try EXPR` binds tighter than binary operators, so this is `(try 1) + 1` — the `try` yields
its `{ok, value, error}` record and `+ 1` fails on it. The error is *true* and useless: it
names a Record in an expression containing no visible record.

**Fix**: when a binary operand is a try-record (a Record with exactly `ok`/`value`/`error`),
say so and name the fix — "`try` binds tighter than `+` — parenthesize: `try (1 + 1)`".
Whether `try` *should* bind looser is a separate, breaking parser question for a later
version.

### D2. The JIT float-kernel eligibility cliff deserves a diagnostic — [FLEET]

The float kernel is disqualified both by any captured outer scalar and by a user-function
call with an `Int` argument; in either case the loop collapses to exact bytecode-VM speed.
My own measurement of the v0.2.0 headline (0.049s at n=20M) used a `Float`-argument callee
with no capture and *did* hit the kernel, so the published claim holds for the shape it was
measured on — the finding is that **the eligible shape is narrower than a user would
guess**, and there is no feedback when you fall off it.

ADR 0026 already says the boundary should be "a diagnostic, not silence". This is the same
argument applied to the float kernel.

## What held up, and is worth not re-testing

Recorded so the next pass does not spend budget re-covering it:

- ~4,000 programs across nine harnesses: a 10,450-expression exhaustive cross product,
  18,100 fuzzed expressions, a 20,001×20 math grid, 1.2M-base bio corpora, 2M-row CSV
  pipelines, a 5.18M-char tokenizer, Life and state machines to 100M steps.
- **One** three-engine divergence in the language core (a `scan` naming bug).
- **Zero** signal deaths in ~3,500 process invocations, apart from B3's allocation abort.
- My own 60-case differential probe: 100% clean — i64 boundaries, 2^53, signed zeros, NaN
  and `missing` through every ordering spelling, empty everything, unicode via literals,
  recursion past the depth cap (plain and mutual), 1,200-deep parse nesting, arity abuse,
  out-of-bounds indexing. Every limit a clean catchable error, never a signal.
- Every v0.2.0 semantic verified on the *shipped* binary: (a1) `argsort` erroring on
  `missing`, (b1) `["b","a"].min()` → `"a"`, (c1) `min_by` propagating `missing` and `[]`
  giving a named error, ADR 0027's retroactive shadowing and above-definition calls, ADR
  0028's query name resolution, `chars()`, `raise`/`try` round-trips, linear append and
  dict-insert.
- Two apparent findings that were the language being *right*, with good hints: string `+` is
  refused ("strings don't join with `+` — use interpolation `"{a}{b}"`, or `xs.join(...)`")
  and `\u` escapes are refused ("strings are UTF-8, paste unicode directly"), with literal
  `café`/`中文`/emoji round-tripping correctly through `chars`/`count`/`reverse`.

## Order of work

1. **B1** — it blinds the oracle, so every later fix is measured through it until it is gone.
2. **B3** — an ADR 0024 violation; the fallible path already exists.
3. **B2** — needs the `missing`-propagation fix *and* an opt-out decision.
4. **C2**, **C3**, **D1** — self-contained, each with a stated fix.
5. **C1** — needs a policy call first.
6. **D2** — a diagnostic, and the natural companion to ADR 0026's.

Then re-run the stress fleet against the 0.2.1 binary before publishing, and re-run the
kernel benchmark suite, which none of this arc's fixes will have moved (see
`bench/kernels/RESULTS.md`'s "What changed" section for why that is expected rather than
suspicious).
